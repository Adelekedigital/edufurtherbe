Backend Standards

A folder you copy into a Python/FastAPI project. No install, no plugin registry, no build step.

v2.2 — two tiers · 11 generic skills + 1 optional · Windows and Unix installers · Python hooks

The one idea that matters

The package is split by who owns each file. That split is what makes updating safe.

Tier 1 — generic Reusable across every project. Overwritten on update. Don't edit these.
  • 11 skills
  • 3 agents, 4 commands
  • hooks, layer checker
Tier 2 — yours True only in this project. Never touched by an update.
  • project-conventions skill
  • its failure-modes log
  • CLAUDE.md, CI thresholds

Anything true only in one project goes in tier 2. That is the whole rule, and it is what lets you take an update without losing project knowledge.

Where the files go

The contents go into your project root. The backend-standards/ folder itself never enters your project — it stays where you unzipped it, as the source you re-run updates from.

your-project/ ├── .claude/ <- .claude/ from the package ├── scripts/check_layers.py ├── .github/workflows/ ├── .pre-commit-config.yaml ├── CLAUDE.md ├── src/ <- your code, untouched └── pyproject.toml

It has to be the root: .claude/ is only discovered there, .github/workflows/ is a path GitHub requires exactly, and pre-commit reads its config from the root. Nested inside a folder, none of it loads.

Never copied in: README.md, both installers, optional/ (only the skill you name, into .claude/skills/), and settings.windows.json.

Collisions in an existing project

Nothing is ever overwritten. Where you already have a file, the package version is written beside it as <name>.new, and every one is listed at the end of the run.

You already haveWhat happens
scripts/, .claude/agents,commands,hooksMerged. Your own files survive.
.github/workflows/deploy.ymlMerged per file — you still receive ci.yml, release.yml, security.yml
.github/workflows/ci.ymlYours kept; ours staged as ci.yml.new
.pre-commit-config.yaml, CLAUDE.mdYours kept; ours staged as .new
.claude/settings.jsonYours kept; staged as .new — merge the hooks block

An unmerged .new file enforces nothingThe installer lists every one at the end of the run precisely so it can't be missed. Diff each pair, merge what you want, then delete the .new.

Setup

1

Unzip it somewhere permanent

Not Downloads — you come back to this folder every time you start or update a project.

PowerShell

Expand-Archive backend-standards-dropin.zip -DestinationPath C:\dev\
cd C:\dev\backend-standards

bash

unzip backend-standards-dropin.zip -d ~/dev/
cd ~/dev/backend-standards && chmod +x install.sh

No shell dependencyThe hooks are Python, not shell scripts — so there is no bash requirement, no chmod on the hooks, and no PowerShell/bash divergence. The same three files run on Windows, macOS, and Linux.

2

Copy it into your project

.\install.ps1 C:\dev\your-project        # PowerShell
./install.sh /path/to/your-project      # bash

Add optional skills your project actually needs:

.\install.ps1 C:\dev\your-project -With tenant-isolation
./install.sh /path/to/your-project --with tenant-isolation

The two installers do the same thingUse whichever matches your shell. install.ps1 additionally writes the Windows variant of settings.json, which calls python and uses %CLAUDE_PROJECT_DIR%; the bash one writes the POSIX variant with python3 and $CLAUDE_PROJECT_DIR. If your interpreter is py, edit those three command strings.

Optional skillInstall when
tenant-isolationSeparate customer organisations share a database and must never see each other's data

Once installed, an optional skill refreshes on every later update — you don't need the flag again.

If the project already has .claude/settings.jsonThe script writes settings.json.new beside it rather than overwriting. Merge the hooks block by hand.

3

Fill in tier 2 — do this first

.claude/skills/project-conventions/SKILL.md ships as a template. It is the highest-value file in the package and the only part you can't download:

  • Settled decisions — with the reason, and what would reopen them
  • Domain vocabulary — words that mean something specific here. Ambiguity in this table is how scope bugs get built.
  • House conventions — where this project overrides a generic standard
  • Guardrails — invariants every build must preserve
  • references/failure-modes.md — what has actually gone wrong here

Why the failure log earns its placeGeneric standards encode what usually goes wrong. The failure log encodes what has gone wrong in this codebase — a far better predictor of the next defect. Add a row whenever something is found the hard way, including near-misses, and write it the same day.

4

Edit the other two project files

CLAUDE.md — the routing table works as-is; change the layout section to describe your actual tree. Keep the file short: it loads on every turn, so anything added is a cost paid by every task.

.github/workflows/ci.yml — set the coverage gate to your current coverage:

--cov=src/your_package     # not src/app
--cov-fail-under=62        # whatever you have today

Do not start at 85%On an existing codebase that fails every PR on day one for code nobody in the PR wrote. Start where you are and raise it a few points a quarter. A gate people route around is worse than no gate.

5

Check where you stand

cd C:\dev\your-project
python scripts\check_layers.py

Violations are fine — you don't have to fix them now. Relax the rules and tighten later:

[tool.check-layers.allowed]
api = ["domain", "infra", "core"]   # permissive for now
domain = ["core"]                   # the one that matters — keep strict
6

Turn on the blocking gates — last

pip install pre-commit
pre-commit install --install-hooks

make check needs make, which Windows does not ship. Run the gate directly instead:

uv run ruff format --check .
uv run ruff check .
uv run mypy src
uv run python scripts\check_layers.py
uv run pytest -q

Order for an existing codebase.claude/ → fill in tier 2 → layer check by hand → CI at current coverage → pre-commit. Advisory first, blocking last. New project: everything on, thresholds at target.

The workflow the skills enforce

Discuss → Confidence Check → Checklist → Definition of Done → Implement → Docs + Commit

Then a Build Verification Gate before moving on. Two constraints do most of the work:

  • The checklist and DoD are approved as text, with no tool calls in the same response. A response that proposes a plan and starts executing it hasn't been approved — it's been announced.
  • Deep checks report findings only. Reviews, debugs, and audits never edit until the fix and its impact are approved.

Commands and hooks

CommandDoes
/reviewRuns the gate, spawns the review agents in parallel, applies whichever skill checklists the diff triggers, then the PR Review Procedure
/shipPre-merge gate: checks, tests, conventional commits
/debugHands a failure to the debugger agent so its searching stays out of your context
/adr-newScaffolds a decision record

Hooks fire invisibly: format on edit, block direct commits to main and --no-verify, run tests touching what changed. All exit cleanly if the tool is missing.

Updating a project later

cd C:\dev\backend-standards
.\install.ps1 C:\dev\your-project       # PowerShell
./install.sh /path/to/your-project     # bash

Tier 1 is refreshed. Tier 2 — your project-conventions, failure log, CLAUDE.md, and CI thresholds — is left alone. Any optional skill already present is refreshed too.

To force everything including tier 2:

.\install.ps1 C:\dev\your-project -Force
./install.sh /path/to/your-project --force

--force overwrites your project knowledgeIt replaces project-conventions and the failure log with the blank templates. Commit before running it.

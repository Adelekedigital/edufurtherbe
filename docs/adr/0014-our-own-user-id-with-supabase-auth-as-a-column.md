# 14. `users.id` is ours; the Supabase auth id is a column

Date: 2026-08-05

## Status

Accepted. **Supersedes ADR 0009 §9**, and only §9 — the rest of that record
stands: Supabase Auth is still the identity provider, the email path still
defaults to a 6-digit code with a link offered as a choice, `auth_codes` and
`password_hash` are still absent, and `auth_identities` still exists.

## Context

ADR 0009 §9 decided that `users.id` **is** the Supabase auth user id, with no
`DEFAULT` on the column. Its argument was economy: "One identifier, no mapping
table, no second id space to translate at the boundary."

That was implemented in the M1 schema, and implementing it is what exposed the
cost. Three things surfaced that the record did not weigh.

**Every foreign key in the system would store a vendor-issued value.** Not just
`users.id` — `user_profiles.user_id`, `admin_users.granted_by`, and in M2–M6
`sessions.mentor_id`, `reviews.reviewed_by`, `credit_transactions.user_id`, and
every other reference to a person across sixty-six tables. The auth vendor's
identifier would be the single most widely propagated value in the database.

**It contradicts this repository's own identifier rule**, which predates ADR 0009
and is stated in `project-conventions` under house conventions:

> **Identifiers:** three distinct spaces, never interchangeable — our internal
> primary key, the `legacy_bubble_id` from Bubble, and any provider-side id.
> Translate at the boundary; do not compare across spaces.

A Supabase auth id is a provider-side id. Making it the primary key collapses two
of the three spaces that rule says must never be interchangeable. ADR 0009 §9 did
not cite the rule or argue against it; the conflict appears to have gone unnoticed.

**It forces an ordering dependency on an external API during the migration.** A
`users` row cannot exist until Supabase has minted that user's id, so M1c would
have to call the Admin API 1,200 times *before* its first `INSERT`, idempotently,
with a Supabase project provisioned and reachable. The load step would fail if the
vendor were down.

ADR 0005 also named auth records as "the sticky part, stickier than the data".
Putting the auth id in every foreign key is the maximal version of that stickiness,
in the place hardest to undo.

## Decision

**`users.id` is our own identifier, generated by `uuid_generate_v7()` like every
other table. The Supabase auth user id lives in `users.auth_id` — a nullable,
unique column, and the only place a Supabase identifier appears in the schema.**

1. **`auth_id` is nullable, and that is load-bearing rather than lax.** A migrated
   user exists before they have ever authenticated. M1c therefore loads 1,200 rows
   without calling Supabase at all, and the migration stops depending on the
   vendor. `auth_id IS NULL` means "has never authenticated", which also makes
   first-login progress across the migrated population a query rather than a guess.
2. **Nothing requires `auth_id` to be present**, indefinitely. An admin-created or
   permanently dormant user is legitimate.
3. **Plain `UNIQUE`, not partial.** PostgreSQL treats nulls as distinct, so any
   number of un-provisioned users coexist; and Supabase never reuses an id, so a
   soft-deleted user cannot block one.
4. **Translation happens once, at the boundary.** A request arrives with a
   Supabase JWT carrying `sub`; the API layer resolves it to `users.id` through
   the unique index, or carries it as a custom claim. Downstream code never sees
   `auth_id`.
5. **`users.id` regains `uuid_generate_v7()`**, so it is time-ordered again.
   ADR 0009 §9 explicitly gave that up because Supabase issues v4.

### Rejected alternatives

**Keep ADR 0009 §9.** Its economy argument is real: one identifier is simpler than
two, and a `sub → id` lookup on every authenticated request is a cost this decision
accepts. Rejected because the cost is bounded and cacheable, while the alternative
distributes a vendor's identifier into every foreign key of the whole schema — and
because the repository already has a rule about exactly this, which §9 contradicts.

**A separate mapping table.** `users` and `auth_accounts` joined on nothing but the
pair. Rejected as strictly worse than one nullable column: a join to answer "who is
this token", and a second row to keep consistent, for no gain.

**Put the auth id on `auth_identities` instead.** Superficially tidy, since that
table already holds provider links. Rejected because `auth_identities` records
*external OAuth providers* — Google, LinkedIn — and a user authenticating by email
code has no row there at all. The Supabase account is not one provider among
several; it is the account.

## Consequences

**M1c is decoupled from Supabase.** The loader inserts users, profiles, languages
and consents with no external dependency, and auth provisioning becomes a separate,
re-runnable step that can happen before, during or after the load — or lazily, at
each user's first login. This removes the single largest operational risk the M1
plan carried.

**A translation step now exists on the authenticated request path.** It is an
indexed unique lookup, cacheable, and removable entirely by putting `users.id` into
the JWT as a custom claim. It is a real cost and it is the one this record accepts.

**"Has this user ever logged in?" becomes answerable.** It was not, under §9 —
every row had an auth id by construction. During cutover, `count(*) WHERE auth_id
IS NULL` is the migration's adoption metric.

**Two of ADR 0009's confirmation items are void.** Its "`users.id` carries no
`DEFAULT`" check is inverted here, and the every-model test that held it now
asserts the opposite. The other confirmations in that record are unaffected.

**Leaving Supabase becomes a one-column problem.** Not free — auth records still
have to move and users still re-authenticate — but no foreign key changes, and no
data migration touches a table other than `users`.

### Confirmation

- **Mechanical:** `tests/unit/test_models.py` asserts `auth_id` is nullable,
  unique, and not part of the primary key. The negation of each is a plausible
  change, which is why all three are asserted rather than the column's existence.
- **Mechanical:** the every-model and every-table id tests assert `users.id` is
  generated like every other table's, so §9 cannot be quietly reinstated.
- **Not mechanical:** nothing verifies that `auth_id` actually holds a Supabase
  id rather than an arbitrary uuid. There is no foreign key to `auth.users` —
  local and CI databases have no `auth` schema — so an orphaned or fabricated
  value is possible and invisible. **M1c needs a reconciliation query**, and it
  does not exist yet. This is the weakest part of this record.
- **Not mechanical:** nothing states which system owns `email` once both
  `users.email` and `auth.users.email` exist, or what happens when they diverge.
  Named here rather than decided, because the first-login flow that has to answer
  it is not built.

### Open questions

- **Where the `sub → users.id` translation lives** — a dependency in `api/deps.py`,
  or a custom JWT claim set by a Supabase hook. Decide when the first authenticated
  endpoint is built, not before.
- **What reconciles `auth_id` against Supabase**, and how an orphan is surfaced.
  Belongs with M1c.
- **Whether email is owned by us or by Supabase**, and what syncs it.
